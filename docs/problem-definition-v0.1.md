# 문제 정의서 v0.1

작성일: 2026-11-03 · 상태: 조사 중인 초안 · 담당: 개인 프로젝트

## 1. 배경과 아직 모르는 것

프로젝트는 제주 안전 관련 보도를 접한 뒤 “안전에 대한 불안 때문에 혼행이나 독채 숙소 선택이 줄었을까?”라는 개인적 의문에서 출발했다.

현재 사건 수 증가, 제주 혼행 수요 감소, 독채 선호 감소를 입증하는 통계는 이 프로젝트에서 확보하지 않았다. 사건 보도, 불안감, 여행 수요, 숙소 선택, 서비스 이용 의사는 각각 다른 변수다. 어느 하나의 답변으로 나머지를 확정하지 않는다.

## 제품 맥락 보완 (2026-11-03)

공식 현재 명칭은 **Vacatio Solution PMS(바카티오 솔루션, 구 파인호스트)**다. ‘안부’는 해당 PMS의 예약·투숙 관리와 고객 안내 흐름에 연결할 수 있는 선택형 기능 제안으로 정의한다. 실제 제공 기능이나 공식 협업으로 주장하지 않는다. 현재 데모는 독립 실행하며 실제 PMS와 연결하지 않는다.

제품 구조와 다음 검증 항목은 [제품 맥락과 기능 제안](product-context-v0.1.md)을 참조한다. 문제 가설과 제주 독채 중심 조사 범위는 유지한다.

## 2. 가설로서의 문제

> 일부 혼행객은 숙박 중 연락이 필요한 상황에서 누가 확인해줄지 불명확하다고 느낄 수 있다. 호스트는 게스트와 약속한 안부 확인을 놓치지 않으면서도 과도한 연락이나 사생활 침해 없이 운영하기 어려울 수 있다.

실제 문제가 존재하는지, 얼마나 자주 발생하는지, 기존 연락 방식으로 충분한지부터 조사한다. ‘수요 감소’가 확인되지 않아도 개별 운영 문제가 존재할 수 있으며, 반대도 가능하다.

## 3. 대상과 상황

- 여행객: 제주에서 혼자 숙박한 경험이 있는 성인. 독채 이용자와 호텔 이용자를 구분한다.
- 호스트: 최근 1인 투숙객을 받아본 제주 독채 운영자. 경험이 없으면 1인 예약 변화 분석에서 별도 분류한다.
- 비교 대상: 1인 고객 경험이 있는 호텔 운영자. 호텔의 상주 인력·야간 대응은 별도로 확인한다.
- 첫 사용 상황: 여행객이 특정 시각의 안부 확인을 선택했고, 약속한 시각과 유예시간이 지나도 응답이 없는 경우.
- 첫 데모: 가상 숙소 1곳, 가상 게스트 3명, 가상 담당자 1명. 실제 예약·위치·도어락·문자·신고 시스템은 연결하지 않는다.

## 4. 검증할 가설

| ID | 가설 | 필요한 증거 | 가설을 약화시키는 관찰 |
|---|---|---|---|
| H1 | 안전 걱정이 일부 여행객의 숙소 선택에 영향을 준다 | 여행객의 최근 선택 과정, 운영자가 직접 들은 구체적 사례 | 구체적 경험 없이 일반적 불안만 언급하거나 다른 요인이 선택을 설명 |
| H2 | 일부 호스트에게 안부 확인·미응답 후속 조치의 업무 부담이 있다 | 최근 처리 사례, 단계, 담당자, 소요시간 | 거의 발생하지 않거나 기존 연락 방식으로 충분 |
| H3 | 여행객은 선택형 안부 확인을 자발적으로 이용한다 | 화면에서 실제 선택, 시간 변경·취소 행동, 이유 | 감시·응답 부담·서비스 기대 불일치로 거절 |
| H4 | 담당자는 미응답 목록과 조치 기록으로 업무를 수행할 수 있다 | 모의 업무 완료, 중복 연락·누락·판단 오류 관찰 | 목록이 오히려 혼란을 주거나 운영 책임을 감당할 수 없음 |

호스트 설문만으로 H1의 인과관계를 입증할 수 없으며, 시장 수요 변화는 별도 통계와 여행객 조사가 필요하다.

## 5. 제공 가치 가설

- 여행객: 누가 언제 확인하는지 알고, 필요할 때 선택·변경·철회할 수 있다.
- 호스트: 약속한 확인 건의 상태와 담당자 조치를 한곳에서 관리한다.
- 제품 방향: 사람이 확인하는 절차를 돕는다. AI가 위험을 판정하거나 안전을 보장하는 제품으로 정의하지 않는다.

## 6. 첫 검증 범위와 제외 범위

포함: 신청, 안내·동의, 시각 설정, 응답, 미응답 표시, 담당자 확인, 기록, 종료·취소.

제외: 실시간 위치 수집, 객실 내 감지, CCTV 분석, 도어락 연동, 자동 경찰 신고, 사고 예측, 지자체 인증, 가격 조정, 상용 과금.

## 7. 진행 판단 기준

초기 소규모 인터뷰는 통계적 검증이 아니라 문제·표현·흐름을 개선하기 위한 탐색이다.

- 실제 사용 경험이 있는 여행객과 호스트 양쪽에서 구체적 문제 사례를 확보했는가?
- 여행객이 정보 공유 범위와 미응답 시 후속 조치를 이해했는가?
- 호스트가 담당 가능 시간과 후속 연락 범위를 설명할 수 있는가?
- 알림이 지나친 걱정·업무·감시 느낌을 만들지는 않는가?

반복되는 실사용 문제가 없으면 기능 확대를 멈추고 문제 정의를 수정한다. 호스트의 대응 가능성이 없으면 게스트에게 약속하는 서비스 범위부터 다시 설계한다.

## 8. 주요 미결정 사항

유예시간, 재알림 횟수, 야간 대응, 담당자 부재·인계, 실제 연락 채널, 운영 중단 시 안내, 데이터 보관 기간, 가격 및 사업 모델. 데모에 쓰는 값은 실제 서비스 정책으로 확정된 것이 아니다.
